为什么需要 Slyztrix

一个操作系统能不能日常用，不取决于内核里有多少子系统，而取决于最普通的一天： 写一份带中文的文档、看一张照片、解压别人发来的压缩包、听一首歌、 打开一个网页、改一行代码、把文件传出去。


SaylterOS 已经跨过了“能启动、能交互、有窗口”的门槛。Slyztrix 处理的是下一道门槛： 软件生态。它不重写内核，也不假装兼容 Windows 二进制； 它把常用软件按可移植性分级，能搬的搬，不能搬的用原生实现替代， 并把每一条限制写在明面上。


判定标准只有一条：连续一周不用别的系统完成日常工作，且不需要“忍一忍”。

移植分级

不是所有软件都用同一种移植方式。先按依赖复杂度分级，再决定路线和投入顺序。

L0 C 运行时底座 · musl libc + syscall 垫片
第一优先级不是再造一套 C 库，而是移植 musl libc（MIT，轻量、静态链接友好）。 上游 C 程序的 stdio、malloc、string、math、time 直接复用，移植工作收敛到 “系统调用适配”这一层。musl 先静态链接进 .slys；动态链接（ldso）后置。
  • musl 静态链接：crt / TLS / stdio / malloc / string / math / time
  • syscall 垫片：open/read/write/close/stat/mkdir → SlyzFS v2，盘符 C:/R:/D:
  • 内存：brk/mmap → 内核堆与页帧池；只读映射提供可执行内存
  • 线程：第一阶段单线程 TLS；pthread 后续映射到协作任务
  • 信号：最小实现（SIGSEGV 交给蓝屏与故障报告）
  • 网络：socket 子集 → 自研 TCP/IP 栈，先阻塞式
  • 图形：GuiExternalHost + win_*，与 libc 解耦
  • 编码：locale 固定 C.UTF-8，GBK 仅在边界转换
L1 纯计算库 · 静态链接进模块
不依赖操作系统服务、只做数据变换的库。编译成目标文件后链接进 .slys 或 .slyzd， 通过 C ABI 直接调用，是最划算的一类移植。
  • 压缩：miniz（zlib 兼容）、libdeflate
  • 图像：stb_image、libpng、libjpeg-turbo（按需裁剪）
  • 数据库：SQLite amalgamation（单文件，无系统依赖）
  • 脚本：Lua 5.4（轻量、易嵌入、替代 Python 子集）
  • 文本：utf8proc 子集、base64、SHA-256（已有自研实现）
  • 字体：FreeType 子集（仅在需要复杂排版时引入）
L2 命令行工具 · 原生实现优先
CLI 工具的复杂度不在算法，而在 POSIX 语义。优先用自研实现覆盖常用参数， 不追求 100% 兼容；确实需要移植时，只搬核心逻辑，I/O 走 musl 与 syscall 垫片。
  • 压缩：zip / unzip / tar / gzip / zstd（解压优先）
  • 文本：grep / sed / awk 子集、diff、hexdump、wc、sort、uniq
  • 编码：iconv 子集（UTF-8 / GBK / UTF-16）
  • 校验：sha256sum / md5sum / crc32
  • 网络：curl（已有）、wget 子集、scp 子集
  • 开发：make 子集、cc 包装、nm/objdump 只读子集
L3 窗口应用 · 复用核心，重写前端
GUI 应用不移植整个工具包。核心算法与数据格式复用，界面改写成 SaylterOS 的窗口与字形 API。VizCormin 已经验证了这条路。
  • 图片查看器：BMP / PNG / JPEG，缩放与旋转
  • 压缩包管理器：列表、解压、打包、预览文本
  • Markdown 预览：解析 + 排版 + 导出 HTML/PDF 文本层
  • PDF 阅读器：文本层渲染优先，复杂排版后置
  • 表格：CSV / TSV 编辑，公式子集
  • 代码编辑：VizCormin（已完成独立窗口化）
L4 攻坚目标 · 浏览器与 Electron 生态
这是 Slyztrix 存在的最终理由：常用软件里最大的一块就是浏览器与 Electron。 如果只能用自己的 HTML 子集，等于把用户和自家应用一起挡在门外。 所以这里不划“不做”，只划阶段和缺口。
  • 阶段一：Electron 应用外壳 —— Node 子集 + 窗口/文件/网络 API，先让自家应用与简单 Electron 应用跑起来
  • 阶段二：JavaScript 引擎 —— 先接 QuickJS 过渡，再评估 V8（JIT 需要可执行内存与更完整的运行时）
  • 阶段三：渲染引擎 —— Chromium content 层 / WebKit / Servo，逐步替换自研 HTML 子集
  • 阶段四：多进程模型 —— renderer 进程隔离，依赖每进程地址空间与 IPC
  • 底座缺口：mmap / fork / exec / 信号 / 线程、动态链接器、GPU 或高性能软件光栅
  • Adobe 全家桶（Photoshop / Premiere / Illustrator / After Effects）暂缓：闭源、GPU 与插件体系重，近期不排期；先用原生图片查看、轻量编辑与 PDF 文本层覆盖基础需求
  • 验收标准：一个真实 Electron 应用 + 20 个主流网站可用，而不是“能打开首页”

承诺

🛡️
不靠改内核换功能
移植只通过模块 ABI、SlyzFS 与窗口宿主接入。内核保持精简，应用崩溃不应拖垮系统。
📐
每个移植都有验收脚本
能启动、能绘制、能退出、无泄漏、无未处理错误。没有验收脚本的移植不算完成。
🔍
限制写在明面上
单地址空间、无 fork/exec、无 GPU 加速、无完整 POSIX。写清楚，才能决定下一步往哪走。
📦
可追溯的包
每个 .spk 带版本、来源、许可证与 SHA-256。安装前校验，升级可回退。
🧭
原生实现优先
能用两百行原生代码覆盖的常用参数，不拖进一个完整上游工具链。复杂度要花在刀刃上。
♻️
保留出处与许可证
移植代码保留上游版权与许可证，修改处标注清楚。不把别人的成果伪装成自研。

日常使用验收

“能日常用”不是感觉，是一张可以逐项打勾的清单：

  • 开机登录，用文件管理器找到并打开一份旧文档
  • 中文输入正常，标点、候选、退格、换行都符合预期
  • 写一份 Markdown 文档并保存，再打开确认内容一致
  • 查看一张 PNG/JPEG，缩放后不糊、不崩
  • 解压一个 zip，文件完整、目录结构正确
  • 播放一首 MP3，暂停、继续、调音量都正常
  • 用 VizCormin 修改一行代码并保存
  • 用 curl 下载文件并核对 SHA-256
  • 窗口可拖动、缩放、最小化、关闭，不残留画面
  • 关机走 ACPI S5，下次启动文件仍在

诚实的边界

当前架构决定的上限

单地址空间与协作式调度意味着没有进程隔离，也没有 fork/exec； 软件渲染意味着 PDF、视频与复杂排版需要谨慎裁剪； 没有完整 POSIX 意味着上游代码需要适配层。 这些限制不会因为“再努力一点”就消失，它们是路线选择的结果。


当前阶段不承诺，但路线明确

不承诺任意 Windows/Linux 二进制直接运行。但 Chromium、Electron、Java、.NET 不是“不做”，而是要先补齐底座缺口：每进程地址空间、mmap/fork/exec、 信号与线程、动态链接器、可执行内存。这些缺口按 L4 的阶段推进， 每补齐一项就解锁一批应用；在此之前，先用自研 HTML 子集与 Electron 外壳保证自家软件可用，再逐步换成通用内核。 Adobe 全家桶是另一类：闭源、GPU 与插件体系重、没有可移植的源码入口， 暂不排期；基础图像与文档需求由原生轻量工具覆盖。


我们承诺

每完成一项，就有一个能跑的应用、一份验收记录、一条写清楚的限制。 先让系统撑起普通的一天，再讨论更大的生态。
